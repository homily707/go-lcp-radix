# Affinity 前缀索引设计

第 1、2 章记录已明确的使用场景、业务要求和优先级，不规定字段、接口签名或并发机制。第 3 章起是基础结构与接口草案，需要依据需求调整。内部驱逐目前只记录行为要求，不确定具体 LRU 容器、批量策略或算法实现。

## 1. 现状与使用场景

### 1.1 索引在路由中的作用

仓库已有基于 `ConcurrentTree` 的路由索引；`pkg/tree` 已实现基础结构及 `New`、`Select`、`Insert`、`Usage`，尚未接入路由。各 workload 的驻留 token 与节点数已在写锁内增量维护；驱逐专用的堆、访问时间元数据和内部方法骨架已移除，内部驱逐待后续实现。

这个索引的实际用途是 affinity 路由：利用历史请求反映的前缀缓存信息，返回各候选 workload 的最佳匹配长度，再由调用方结合 workload 负载选择路由。候选应覆盖不同匹配长度，不能只保留全局最大 LCP 的同分 workload。它不以普通 KV 存取或完整保存请求历史为目标。

原始请求是 token 序列。为节省内存，调用方提前按 message 切分，为每个 message 计算 hash，并记录其原始 token 数；索引实际接收、保存的是这些 Chunk，不保留原始 token。前缀匹配以完整 Chunk 为单位，对外的匹配长度、缓存占用和驱逐量按命中或驻留 Chunk 的原始 token 数之和计算。

每次路由选中的服务节点，即 workload，在索引中用 `Workload` 结构体表示，以 `ID` 为唯一身份：同 ID 即同一 workload。`Group` 与 `Capacity int` 是随附属性，不构成身份，随该 ID 最近一次登记刷新；`Capacity` 是该 workload 的 token 容量上限，再次 Insert 同 ID 可动态更新。负载等其他可变信息放在外部。这里的 workload 与 radix tree 的结构节点是两种不同对象。

请求流程是：

1. 请求到来，独立执行 Select，得到前缀匹配信息和多个候选 workload。
2. 根据候选 workload 的负载选择本次路由节点。
3. 请求结束后，再独立 Insert，记录已完成上下文的 Chunk 序列及实际选中的 workload；树在同一次写操作内按容量自动驱逐。

Select 与 Insert 不是一次不可分割的操作；查询时不应提前把请求记为已完成的历史。

调用方应将已完成的 assistant 回复纳入登记，并保证它与下一轮请求中的对应 message 使用一致的切分和 hash 口径；TokenCount 应尽量一致，但差异不会使相同 Hash 的 Chunk 失配；树中保存的 TokenCount 以首次登记为准，调用方需保证同 Hash 的 TokenCount 一致，否则占用记账会偏离实际。若只登记请求、不登记回复，会低估模拟占用和后续命中长度，也可能改变候选排序。这里登记的是模拟缓存信息，不保证完整复刻真实引擎的 KV 状态。

### 1.2 实际负载与多轮对话

| 已知特征 | 场景含义 |
| --- | --- |
| 长公共前缀、低分叉 | 很多请求复用已有上下文，结构分裂相对少见 |
| 大部分写入是多轮对话追加 | 新请求通常在已有 token 序列后继续增长 |
| Select 极高频 | 查询成本和并发下的延迟是主要关注点 |
| Insert、驱逐也高频 | 需要考虑持续更新时的性能，不能只看静态树的纯读吞吐 |
| 缓存容量在稳定阶段通常不变 | 插入与驱逐持续交替发生；容量变化由下一次同 ID Insert 带入 |

多轮追加时，共享前缀在同一 workload 内不重复计费。不要求保留每轮追加边界，倾向合并同一 workload 连续追加形成的片段，减少节点、重复驻留元数据和查询路径开销；合并必须保持分叉及各 workload 的实际覆盖边界。切换 workload 后，旧 workload 仍应保留候选资格，直到对应的模拟缓存被驱逐。一个会话可能切换 workload，不能只保留最后一个 workload。

追加完整 message 时，Chunk 序列仍是前缀追加；修改已有 message 的内容会改变其 hash，在 Chunk 层面形成分叉，即使原始 token 层面只是延长最后一条消息。

保留旧 workload 的候选资格不代表它一定拥有最新完整上下文。路由需要的是有用的前缀亲和信息，而非每轮请求都必须成为一条独立、永久保留的历史记录。

### 1.3 KV cache 驱逐场景

驱逐是在模拟各 workload 上的大模型 KV cache，不是按请求删除整条历史 entry。每个 workload 的容量与驻留 token 总量必须独立、准确；容量达到或超过上限时，由树内部按 LRU 自动选择冷数据并驱逐。

要求精确的是每个 workload 的总 token 记账，不是每次驱逐的 token 粒度。设计倾向粗粒度驱逐：优先按较大片段或多个相连节点批量清理，减少结构与驱逐维护开销；允许实际释放量大于腾出空间所需的量，不要求拆分片段以凑出精确释放量，也不要求严格逐节点执行全局 LRU 排序。每轮请求的结束位置不是必须保留的驱逐边界。

- 可驱逐性按某个 workload 自己的缓存前缀关系判断。其他 workload 仍保留更长前缀，不应阻止当前 workload 驱逐自己的后缀。
- 可从 LRU 选出的冷叶子开始批量清理。“连着的叶子节点”包括沿同一分支删除后缀后，刚成为该 workload 叶子的父节点；允许在同一批次继续向上清理，不要求每删一个节点就重新参与全局排序。
- 父节点仍有该 workload 的其他驻留子节点时不能删除。批量清理不要求无条件删除整条会话到根；满足条件时，一次连续驱逐也可能覆盖整个多轮会话。
- 某个 workload 的缓存被驱逐，不应同时删除其他 workload 对同一前缀的缓存信息。
- 批量驱逐必须按实际移除的驻留 token 数扣减该 workload 的占用，不能用目标释放量或估算值代替实际释放量。

例如，以 A、B、C、D 各表示一个 Chunk，w1 只保留 `AB`，w2 保留 `ABCD`，那么 `AB` 已经是 w1 视角下的叶子；w2 仍有后缀不影响 w1 的驱逐资格。这里描述的是缓存关系，不规定索引采用共享树还是其他物理布局。

已确定的职责分配是：调用方配置容量，索引保存容量并负责准确记账、LRU 选择和批量驱逐。调用方不需要计算超额、显式触发驱逐、维护缓存片段 ID 或同步叶子变化。先明确需求，当前不实现驱逐算法，也不预先选定堆、链表、批次大小或低水位。

各 workload 的容量来自各自的 `Capacity`，可有不同限额；同 ID 再次 Insert 更新容量，占用和驱逐各自独立，不共享一份总预算。容量不大于 0 表示不保留缓存记录，而不是无限容量。占用记账已实现，驱逐尚未实现，因此当前更新只刷新配置，占用可能超过容量，也不会立即清理已有记录。

### 1.4 与现有分片路由的关系

当前 `internal/router` 的 Insert、UpdateLRU 按推理 endpoint ID 做一致性哈希，将同一个 endpoint 的写入交给同一个 radix-server；查询可以广播到各分片，再按 MatchLength 排序、按 endpoint 去重。代码中表示索引分片的 workload 与本文表示推理 endpoint 的 workload 含义不同。

路由表一致、拓扑稳定时，一个推理 workload 的模拟缓存由所属分片管理，无需把该 workload 的容量平分给所有分片。扩缩容后的归属变化、旧分片残留，以及多个 router 路由表不一致时的迁移或失效处理，属于集成层职责；单进程树不协调跨分片占用。接入时必须明确这些处理方式，不能假设广播查询能解决缓存迁移或容量一致性。

## 2. 实战要求与优先级

### 2.1 重要的要求

| 要求 | 具体含义 |
| --- | --- |
| 查询与写入独立 | Select 服务于当前路由，Insert 在请求结束后独立执行 |
| Chunk 匹配、token 计费 | 只按完整 message 的 hash 匹配；TokenCount 不参与相等判断，匹配长度与缓存预算仍按 token 数计算，不能用 Chunk 个数代替 |
| 保留多个路由候选 | 返回不同匹配长度及同分的 workload，每个 workload 取其最佳匹配长度，由调用方权衡亲和程度与负载 |
| 保留切换前的 workload 信息 | 新 workload 的记录不能简单覆盖旧 workload 仍然拥有的缓存前缀 |
| 各 workload 独立模拟缓存 | 驱逐资格和占用属于相应 workload，不能用全局是否有子节点代替某个 workload 的叶子条件；树在写入时自动维持各 workload 的容量上限 |
| 总量精确、驱逐粗粒度 | 每个 workload 的总 token 占用和实际释放量必须准确；容量满时按 LRU 驱逐，倾向较大片段及相连叶子的批量清理，允许多释放一些 |
| 支持后缀驱逐与向上级联 | 删除后需要体现父前缀是否仍驻留、是否成为新的驱逐候选；不能套用删除完整请求 entry 的语义 |
| 占用与生命周期可查询、可清理 | 索引维护准确占用，支持清空一个 workload 的记录，并提供驻留 token 及节点数；不把 LRU 容器作为公开统计契约 |
| 混合负载下的性能 | 优先控制高频 Select 的成本，同时使常见追加和持续驱逐的写入、分配成本可接受 |
| 实现复杂度可控 | 优先用批量驱逐控制成本，不追求精确释放到 token 或逐节点严格排序；外部无需管理 entry ID 或结构变化通知 |
| 并发执行安全 | 放宽匹配结果的一致性，不等于允许数据竞争、损坏结构或误删其他 workload 的缓存信息 |

### 2.2 不优先追求的保证

- **强一致性和立即可见。** 允许毫秒级的可见性延迟，不要求 Select 获得完整的全树原子快照。
- **每次查询都达到严格、瞬时的最优 LCP。** 偶发地把接近的 `abc`、`abcd` 当成相近匹配，业务影响较小；没有必要只为这类少数情况付出很高的实现或同步成本。
- **逐轮完整保留历史请求。** 需要保留的是对路由仍有价值的缓存前缀和 workload 关系，历史请求数量与索引记录数量不必一一对应。
- **完整复刻推理引擎内部状态。** 当前是在模拟 KV cache 驱逐，未要求本索引保存实际 KV 数据或与真实引擎的每次变化严格同步。
- **精确驱逐粒度。** 不要求刚好释放所需的 token 数，也不要求每个叶子删除后立即重新比较全局 LRU；允许从冷叶子开始连续批量清理。该放宽不影响 workload 总占用记账的准确性。

message 级表示本身不识别两个不同 message 内部的公共 token 前缀，返回的 token 长度仅涵盖完整命中的 Chunk；这与并发导致的短暂不一致是两个不同边界。

这些容忍范围不等于允许长期、无界地高估一个 workload 的缓存覆盖。用户允许的是少数情况的小差异，目前没有指定可接受的 token 偏差上限，也不应自行把某个数值写成需求。

### 2.3 职责边界与尚未指定的参数

索引负责前缀匹配、workload 缓存驻留关系和准确占用记账、按 LRU 自动批量驱逐与清理。调用方负责候选 workload 的负载选择、容量配置，以及下线或重启时的生命周期协调。驱逐是内部机制，不公开 Evict 或 Trim 接口。

首版以请求完成后的 Insert 作为访问时间更新点，近似 LRU；Select 保持纯读，不把全部候选 workload 当作实际被访问。索引内的缓存片段身份和 LRU 元数据属于实现细节，不作为外部需要维护的对象。

当前尚未指定：

- workload 数量、每请求 message 数及每个 message 的 token 数分布、实际读写比例、容量规模。

已给定的负载参数：Select 约 1000 QPS，48 核；Select 允许被写操作阻塞，单次阻塞不超过 500 ms。它与第 2.2 节的毫秒级可见性延迟是两项不同的约束。
- LRU 元数据与容器、批次大小、是否使用低水位及具体连续清理策略。当前只要求整节点批量驱逐，不要求部分片段驱逐。
- 业务侧候选数量上限及允许的匹配偏差。候选上限由初始化参数 topK 指定，Select 返回按匹配长度排名的前 topK 个正 token 候选，同分任取；不足时保留次优层候选。

同步机制、小集合的容器和切换阈值属于满足上述要求的实现选择。按上述负载参数，已选定整树 RWMutex 与合并追加，见第 3 章和第 6.1 节。以下章节区分当前基础实现与后续草案；tree.go 已保存容量配置并维护占用记账，尚未实现驱逐。
