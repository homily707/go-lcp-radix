驱逐的难点主要不在 LRU 容器选哪种，而在于"某个 workload 的叶子"这个概念要随分裂、合并正确地转移。所以下面先列出不管选哪个方案都要做的基础，再给三个选冷叶子的方案，最后是批量策略和坑。以下都是基于当前 `tree.go` 的分析，没有改代码。

## 一、所有方案都要先做的基础

**1. 定义"workload 视角的叶子"（下文简称 w-叶子）**

节点 n 是 w 的叶子，当且仅当 w 驻留在 n 上，并且 n 的任何子节点都没有 w。驱逐永远只从 w-叶子开始：把 w 从 n 的驻留列表里去掉，w 的占用减去 `n.tokens`，节点数减 1。之后 n 的父节点可能变成新的 w-叶子，于是可以沿同一条分支继续往上清理。这正是 README 要求的"后缀驱逐加向上级联"，而且只动 w 自己的驻留，不影响其他 workload。

**2. 需要新增的结构信息**

| 需要 | 原因 | 做法 |
| --- | --- | --- |
| 父指针 `node.parent` | 向上级联和删除空节点时要找到父节点，现在的树只能从根往下走 | 建叶子、分裂、合并时维护 |
| 每条驻留记录的子引用计数 `childRefs` | 判断是不是 w-叶子要 O(1)，不能每次扫描所有子节点 | w 登记到子节点时，父节点上 w 的计数 +1；驱逐时 −1 |
| 驻留记录改为可寻址 | LRU 句柄要稳定地指向某条驻留记录，而 `[]residency` 在 append 扩容时会搬家 | 改成 `[]*residency`，或者驻留记录持有一个堆上分配的句柄对象 |

**3. 驱逐之后的结构清理**
- 节点的驻留列表变空：按不变式它必然没有子节点，直接从父节点摘掉这条边。父节点这时可能只剩一个子节点、且两者驻留集合相同，需要合并；子节点从 map 退回切片的降级逻辑也在这里补上。
- 节点的驻留列表不空：去掉 w 之后，它和唯一子节点的驻留集合可能变得相同，同样需要合并。
- 以上两种都可以复用现有的 `mergeOnlyChild`，但它要多做一件事：迁移 LRU 句柄，见第四节第 1 条。

**4. 驱逐的触发点**
- Insert 结束时，只检查本次登记的 w。一次 Insert 只会增加 w 的占用，唯一的例外是下面这一条。
- 刷新 TokenCount 可能让共享前缀上其他 workload 的占用变大，甚至超额。可以选择顺带把它们记下来一起驱逐，或者接受它们要等到自己下一次 Insert 时才被收回。
- `intern` 时如果 `Capacity` 变小，也要立即检查一次。

## 二、选冷叶子的三个方案

### 方案 A：每个 workload 一条侵入式 LRU 双向链表（推荐）
- 每个 workload 维护一条链表，只挂它自己的 w-叶子驻留记录。
- 访问时：Insert 把本次 key 末端节点上 w 的记录移到表头。
- 驱逐时：从表尾取出最冷的叶子删掉，再沿父指针向上连续清理：父节点上 w 的记录如果 `childRefs` 变成 0，就继续删。一直清理到占用降到目标值以下。
- 父节点在级联中变成 w-叶子但本批没有删到它时，把它插回表尾，也就是继承被删子节点的冷度。
- 优点：每步都是 O(1)，行为确定，容易写精确的测试；"向上清理一串节点"本身就是天然的批量。
- 缺点：分裂和合并时，叶子身份会在节点之间转移，要同步移动链表句柄，见第四节第 1 条。这是本方案主要的实现成本。

### 方案 B：时间戳加懒删除的最小堆（每个 workload 一个）
- 每条驻留记录带一个 `lastAccess`（全局单调递增的计数器即可），访问时只更新时间戳，再往堆里压一个新条目。
- 驱逐时弹出堆顶，如果条目已经过期（时间戳对不上、已经不是叶子，或节点已被合并），就丢弃继续弹。
- 优点：分裂、合并时不用搬移容器里的条目，只需复制时间戳；过期条目在弹出时自然被过滤。
- 缺点：堆里会不断积累过期条目，需要定期重建或压缩；每次访问都要一次 O(log n) 的压堆和一次分配；过期判断的逻辑本身也容易出错。

### 方案 C：时间戳加采样的近似 LRU（类似 Redis 的做法）
- 每个 workload 维护一个 w-叶子集合：用一个切片，外加每条记录在切片里的下标，删除时和末尾交换，做到 O(1)。
- 驱逐时随机抽 k 个（比如 5 个）叶子，淘汰其中 `lastAccess` 最小的。
- 优点：数据结构最简单，访问时只写一个时间戳。README 明确允许不严格的全局 LRU。
- 缺点：带随机性，测试需要固定随机种子，写起来不够直观；叶子很多时抽样质量会下降；集合的下标同样要在分裂、合并时维护，所以实际省掉的复杂度不如看上去多。

**三个方案对比**

| | A 链表 | B 懒删除堆 | C 采样 |
| --- | --- | --- | --- |
| 访问成本 | O(1)，搬移链表节点 | O(log n)，还要一次分配 | O(1)，只写时间戳 |
| 驱逐成本 | O(1) 每个节点 | 摊还 O(log n)，还要跳过过期条目 | O(k) |
| 分裂、合并时的维护 | 转移句柄 | 只复制时间戳 | 转移下标 |
| LRU 精度 | 精确，仅限 w-叶子 | 精确 | 近似 |
| 可测试性 | 最好 | 中等 | 需要固定种子 |

## 三、批量与水位

- **低水位**：超过 `Capacity` 时，一直驱逐到 `Capacity × (1 − α)` 以下（比如 α = 10%）。这样可以避免每次 Insert 都只清一点、频繁触发驱逐。README 允许多释放一些。
- **整节点驱逐**：不拆分 segment，一个节点就是一个驱逐单位。独占叶子已经把多轮追加合并成一个大 segment，一次就能释放一整段会话。
- **精确扣减**：每删一个节点就按它当时的 `n.tokens` 扣减。TokenCount 刷新已经把差值同步到了所有驻留者，所以扣减后记账是精确的。

## 四、要注意的坑

1. **叶子身份的转移（最容易出错）**
   - 分裂：原节点上每个 workload x 如果原本是 x-叶子，分裂后它的叶子身份转移到后缀节点；前缀上 x 的 `childRefs` 变成 1。这要对所有驻留者都做一遍，是 O(values) 的，和分裂时本来就要复制驻留列表同一量级。
   - 合并：子节点的驻留记录会消失。如果其中某条是叶子，它的 LRU 句柄或时间戳要转给父节点上对应的记录。这里需要把父子两边的记录一一对应起来：简单做法是两层循环，但共享节点上驻留者可能很多；也可以在记录上保存一个"同一 workload 在父节点上的记录"指针，用来 O(1) 对齐。
2. **访问时间只打在最深处**：只更新本次 key 末端那个节点上的记录，不去刷新整条路径，否则共享前缀节点上会有 O(驻留者数) 的查找。祖先节点的冷热由级联时继承来近似，这在 README 的容忍范围内。
3. **不要破坏"子节点的 workload 是父节点的子集"**：只能删 w-叶子上的 w，删非叶子会让子节点多出父节点没有的 workload，Select 的去重和 register 提前停止都依赖这个不变式。
4. **`Capacity <= 0`**：等驱逐做完，这种情况就等价于"登记后立即全部清空"。可以在 Insert 开头直接跳过，但要先把现有测试改成带容量，否则大部分测试会失败。
5. **Remove 和 `workloads` 映射**：Remove(id) 等于"反复驱逐这个 workload 的叶子，直到它的节点数为 0"，之后才能把它从 `workloads` 里删掉，这样才满足 `intern` 注释里"没有残留引用"的前提。
6. **写锁的持有时间**：驱逐和 Insert 在同一次写锁里完成。低水位清理会让单次 Insert 变长，要确认最坏情况仍满足"Select 被阻塞不超过 500 ms"。可以给单次驱逐的节点数设上限，没清完的留到下一次 Insert 继续。
7. **测试**：把 `checkInvariants` 扩展到覆盖父指针、`childRefs`、LRU 成员关系（在链表里的恰好是全部 w-叶子）、每个 workload 的占用不超过水位，再在随机测试里加入带容量的 workload。

## 建议

先做第一节的基础（父指针、`childRefs`、可寻址的驻留记录），这一步和选哪个方案无关，可以单独提交，用 `checkInvariants` 验证。然后选**方案 A**：它的主要成本是分裂、合并时转移句柄，而这部分不管选哪个方案都绕不开；除此之外 A 最简单、行为确定，最容易测试。
